Module Overview

This module examines how xv6++ organizes persistent data into files and directories and maintains file-system consistency when multiple processes operate concurrently or the system crashes.

You will study the major file-system layers, including disk blocks, the buffer cache, write-ahead logging, inodes, directories, path-name lookup, file descriptors, and system-call integration.

This module has two required assessments:

  • Chapter 10 Quiz: File System — 15 points
  • Seek Lab — 50 points

The lab focuses on the open-file layer: you will implement a system call that changes where the next read or write begins.

Why This Module Matters

A file system must do much more than store bytes. It must provide meaningful names, organize files into directories, share files safely among processes, manage limited disk space, and preserve consistency when operations are interrupted by a crash.

Even a simple operation such as creating and writing a file may require several coordinated updates:

  • allocate an inode,
  • initialize inode metadata,
  • add a directory entry,
  • allocate data blocks,
  • update free-space information,
  • write the changes to disk safely.

Chapter 10 shows how xv6++ divides these responsibilities into layers. The seek lab asks you to extend the interface programs use to access file data, while preserving the existing behavior of the underlying file system.

Big Idea

The xv6++ file system builds high-level abstractions such as files, directories, links, and file descriptors on top of disk blocks while using locks and write-ahead logging to preserve consistency.

A file's contents and size are persistent state. An open-file object's current offset is in-memory state. Seeking changes that offset without changing the file's contents or size.

Key Vocabulary

Block A fixed-size unit transferred between memory and disk.
Superblock On-disk metadata describing the layout and size of the file system.
Buffer cache An in-memory cache of disk blocks that also synchronizes access to them.
Write-ahead log A reserved disk area in which an update is recorded before being installed in its normal location.
Transaction A group of related file-system updates that should be committed atomically.
Commit The point at which a logged transaction is recorded as complete and recoverable.
Recovery Replaying a committed transaction after a crash.
Bitmap A structure that records which disk blocks are free or allocated.
Inode A file-system object containing a file's type, size, link count, and block addresses.
Direct block A data block whose address is stored directly in the inode.
Indirect block A block containing additional data-block addresses.
Directory entry A mapping from a name to an inode number.
Path-name lookup Resolving a path one directory component at a time.
File descriptor A small per-process integer referring to an open-file object.
Open-file object A kernel object containing the file type, access modes, current offset, and inode or pipe reference.
File offset The byte position at which the next read or write begins; stored in the open-file object.
Seek An operation that changes the current file offset without reading or writing file data.
Whence The argument selecting the reference position from which a seek displacement is measured.
EOF End of file. For a file of size N bytes, offset N is immediately after the final byte.
Signed displacement A positive, zero, or negative byte distance from a reference position.
Hard link An additional directory entry referring directly to the same inode.
Symbolic link A special file containing a pathname to another file or directory.
Dangling symbolic link A symbolic link whose stored target path cannot be resolved.

Understanding File Positioning

Suppose a file contains ABCDEFGHIJKLMNOP, with a size of 16 bytes. Its first byte is at offset 0, its last byte is at offset 15, and EOF is at offset 16.

The following operations happen in sequence:

Operation Offset Afterward Meaning
seek(fd, 4, SEEK_SET) 4 The next read starts at E.
Read one byte 5 Returns E and advances the offset.
seek(fd, 2, SEEK_CUR) 7 Moves two bytes forward from the current offset of 5.
Read one byte 8 Returns H and advances the offset.
seek(fd, -2, SEEK_END) 14 Moves to two bytes before EOF.
Read one byte 15 Returns O and advances the offset.
seek(fd, -17, SEEK_END) 15 (unchanged) The requested position is -1, so the call fails.

Arithmetic Hint

The inode size and stored offset are unsigned, but the displacement is signed. Convert the base before adding:

long long tmp = (long long) ip->size + offset;

For SEEK_CUR, use the current off as the base. Check that the resulting position is between zero and file size before storing it.

A cast around the completed sum is too late: (long long) (ip->size + offset) still performs the original unsigned addition first. The Seek Lab instructions include a full worked arithmetic example.

Hard Links and Symbolic Links: Chapter Background

Links remain part of the chapter reading and quiz. You do not implement symbolic links in the seek lab.

Feature Hard Link Symbolic Link
What it stores A directory entry referring directly to an inode number A pathname stored as file data
Target requirement The target inode must exist when the link is created The target may be missing when the link is created
Effect of target removal The inode remains while another hard link or open reference exists The symbolic link may become dangling
Resolution The directory entry identifies the inode directly The stored path must be resolved when the link is followed
Possible cycle Not through ordinary file hard links Yes, symbolic links can refer to one another cyclically

Common Trouble Spots

  • Thinking that the buffer cache is only a performance optimization. It also synchronizes access to disk blocks.
  • Confusing a disk block with a memory page.
  • Thinking that a committed transaction has already been installed in every home location.
  • Forgetting that recovery replays only a committed log transaction.
  • Confusing an inode with a file name. Names are stored in directories, not in the target inode.
  • Confusing an on-disk inode with its in-memory cached representation.
  • Confusing a process file descriptor with the shared open-file object it references.
  • Forgetting that duplicated descriptors may share the same file offset.
  • Assuming that unlink always destroys the inode immediately.
  • Confusing a hard link with a symbolic link.
  • Confusing the current offset with the file size. SEEK_CUR and SEEK_END use different reference positions.
  • Forgetting that a successful read or write advances the current offset.
  • Adding a negative displacement to an unsigned base before converting to a wider signed type.
  • Negating the most negative signed integer to check a bound; this can overflow.
  • Updating the offset before checking whether the request is valid.
  • Rejecting exact EOF, or allowing positions beyond EOF despite this lab's bounds.
  • Returning the new position instead of the required success value 0.
  • Using an inode pointer before rejecting pipes and devices.
  • Skipping the inode lock because seeking does not write disk data. Shared in-memory state still needs synchronization.
  • Adding a log transaction to seek even though it only updates the open-file offset. Transactions remain necessary for operations that modify persistent file-system state.
  • Leaving an inode or buffer locked on an error path. Use the existing RAII guards correctly.

Final Reminder

Keep the file-system layers in mind. An inode-backed read follows a path such as:

read system call
    -> file descriptor
    -> open-file object and current offset
    -> inode and file-relative block mapping
    -> buffer cache
    -> disk driver when disk I/O is needed

Operations that modify persistent file-system state also use the logging layer to make their updates recoverable. Not every file operation performs disk I/O or starts a transaction.

The seek lab focuses on this shorter path:

seek system call
    -> validate descriptor and file type
    -> lock inode
    -> calculate and validate requested position
    -> update the open-file offset
    -> unlock and return

Seeking does not modify the file's data or size and needs no log transaction. The inode lock protects the position calculation and update; acquiring that lock may load inode metadata if it is not already cached.

Complete the reading and quiz before beginning the lab. Understanding open-file objects, inode size, shared offsets, and locking will make the implementation substantially easier.
